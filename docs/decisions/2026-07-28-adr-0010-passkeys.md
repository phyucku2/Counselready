# ADR-0010 — Passkeys (WebAuthn) for phone-first sign-in

**Date:** 2026-07-28
**Status:** Accepted
**Owner decision:** the *requirement* came from the owner (phone-first, Face ID)

## Problem

Most uploads will come from a phone, and typing a password plus a six-digit code on a
phone, repeatedly, during a stressful period, is the kind of friction that makes people
stop using a tool. The owner asked whether Face ID could be used.

## Decision

**Passkeys (WebAuthn/FIDO2), not "biometric login".**

The distinction matters. Face ID is not authentication to a server — the biometric never
leaves the device and we never see it. What Face ID does is unlock a private key held in
the device's secure enclave, which then signs a challenge we issue. We verify a
signature. So "sign in with Face ID" is really "Face ID unlocked a passkey".

Consequences worth stating:

- **We store no biometric data.** Only a public key, which is not secret. That is also
  why this adds none of the obligations that come with handling biometric identifiers.
- **A passkey is phishing-resistant.** It is bound to our origin, so a convincing fake
  login page cannot use it. A TOTP code typed into that same fake page works fine for
  the attacker — this is a genuine security gain over the factor built in ADR-0008, not
  only a convenience one.
- **`user_verification=REQUIRED`** means the authenticator must confirm the human, not
  merely that the device is present. That is what lets a passkey satisfy both factors at
  once: possession and the person were proved before the assertion reached us.

### TOTP stays

Passkeys are the fast path, not the only path. TOTP survives a lost phone, works on a
borrowed laptop, and does not depend on an Apple or Google account the user may be in
the middle of separating from. Recovery codes still cover the worst case.

### Challenges are server-side and single-use

Held in `passkey_challenge`, deleted on use. A challenge that verified twice would let a
captured assertion be replayed — tested directly.

### Sign-in does not disclose whether an account exists

`login/begin` returns a well-formed challenge for an unknown address with an empty
credential list, matching the rule established in ADR-0007.

## The hazard this does not solve

Two things are common in exactly the situation these users are in, and both undercut
device-bound authentication:

1. **Someone else may be enrolled on the phone.** iOS allows an alternate appearance and
   both platforms allow multiple fingerprints; partners enrol each other routinely, often
   years earlier and then forgotten. If the ex is enrolled, Face ID opens the account.
2. **Synced passkeys inherit the sync account.** A passkey in iCloud Keychain or Google
   Password Manager exists wherever that account is signed in — including a device
   belonging to someone the user is separating from.

Neither is fixable in code. What the product can do, and what the schema now supports, is
**surface it**: `passkey.backed_up` records whether a credential is synced, and it is
returned by the list endpoint so the UI can say so plainly. The enrolment screen should
also prompt the user to check who else can unlock the phone — that copy is owner-and-
counsel wording, not something to invent here.

This is also why passkeys **augment** rather than replace the password + TOTP path.

## Consequences

- `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGIN` must match the real domain in production. The
  origin binding that makes passkeys phishing-resistant is exactly what breaks if these
  are wrong, so they cannot be guessed at deploy time — and they connect to the domain
  decision the owner has not yet made.
- No pruning job yet for expired challenges; they accumulate. Small, but real, and it
  belongs with the other cleanup work deferred to the queue portion.
- Tests drive a software authenticator (ES256 key pair, signed attestation and
  assertions) rather than mocking verification. A mock would hide precisely the parts
  worth testing: signature checking, origin binding, and challenge consumption.
