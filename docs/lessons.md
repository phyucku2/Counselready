# Lessons — mistakes turned into rules

Append-only. Each entry is a **finding-class we actually hit** (or a risk identified in
research before it could bite), rewritten as a **one-line preventive rule** so it never
recurs. Newest at the bottom. Consult this list before building; add to it every time
review or CI catches a class of mistake not already here.

Format: `- **<short name>** — <one preventive rule>. (<where it came from>)`

## Rules

- **An uncited generated statement is a defect, not a rough edge** — every event, flag, and observation must resolve to document + page + passage before it can render; build the citation into the storage schema so an uncitable claim is unrepresentable rather than merely discouraged. (ADR-0001/0002; the 2025 sanction wave — ~712 decisions on AI-hallucinated content, ~90% written in 2025, including South Florida)
- **Never generate legal authority from model knowledge** — the product analyzes documents the user supplies; a statute, case citation, or rule the model recalls is exactly the failure mode courts are sanctioning. Analyze the file, never author the law. (ADR-0001 §2)
- **The name of the risk is overclaiming, not the software** — the FTC's $193,000 DoNotPay order turned on "performs like a lawyer" marketing, so review copy (app store, landing page, in-product headings, push notifications) against the §1 line with the same seriousness as code. A compliant engine behind advice-flavored copy is still the violation. (market research §5)
- **Two accounts of one event are two claims** — never merge conflicting dates or descriptions into a single "fact"; render both, attributed, and let the human judge. Silent reconciliation manufactures evidence. (CLAUDE.md §2)
- **Tone analysis is a bias surface before it is a feature** — dialect and non-native English score as more hostile on off-the-shelf tone classifiers, so language review ships quote-based, after a documented bias evaluation, and never as a score attached to a named person. (ADR-0001 Phase 4)
- **Sensitive-by-default beats sensitive-by-tag** — a family court file mixes medical, financial, and minors' data on adjacent pages, so apply the strictest handling to the whole corpus rather than to pages a classifier tagged. A misclassified page must not be a privacy incident. (CLAUDE.md §3)
- **The threat model runs in both directions** — the same pattern-documentation that helps a survivor evidence a case helps an abuser surveil and harass; account takeover by an ex-partner is a life-safety event, so MFA, login alerting, and no shared-household accounts are launch requirements, not hardening backlog. (CLAUDE.md §3; DV-advocate lens)
- **A jurisdiction assumption is a bug in waiting** — Florida terminology, document types, and local rules go behind the jurisdiction-profile seam from the first parser, because a rule hardcoded in Phase 1 is a rewrite in Phase 5. (CLAUDE.md §7)
- **Store-blocking requirements are built early or they block you late** — account and data deletion is a hard app-store rule for any app collecting user data; schedule it in Phase 0 rather than discovering it at submission. (roadmap 0.4)
- **No public preview URLs for a product holding court files** — a per-PR preview deployment is a convenience for a marketing site and a disclosure risk here; previews, if wanted, are authenticated. (ADR-0002)
- **A startup fail-fast belongs on the serving path, never in `Settings` construction** — a config-time validator fires in every context that imports config, including `alembic`, so a guard that demands serving-only configuration breaks `alembic upgrade head` (which legitimately holds a database URL and nothing else). Put deployment-context guards in the FastAPI lifespan, where only a serving process runs them. (ADR-0003; `app.main.check_serving_configuration`)
- **Generated files must be lint-clean on arrival, or the generator is the bug** — Alembic renders every migration from `script.py.mako`, so a template that emits single-quoted strings, a trailing space, or an import order the linter rejects makes CI red for anyone who runs `alembic revision`. Fix the template and the tool config (a local `alembic/` directory makes ruff classify the installed `alembic` package as first-party — `known-third-party` corrects it), then prove it by generating a throwaway revision and running the real gates over it. (Phase 0.2)
- **A probe reports state, it never raises** — readiness must translate an unreachable dependency into a 503 body, not let the exception escape into the probe response; that is the one place a catch-all `except Exception` is correct. (`app.db.session.database_is_reachable`)
- **A nullable column plus a convention is not a rule — use a conditional CHECK** — "document-derived events cite a passage" enforced by a nullable `passage_id` and good intentions permits exactly the row that must never exist. A two-branch CHECK on the provenance discriminator makes each shape's companion column mandatory and the other shape's impossible, so no future write path can produce a user's typed note wearing a document's authority. (ADR-0005 `case_event`)
- **Store how precisely a date is known, not just the date** — sources say "in March" or "last spring" constantly, and a bare timestamp renders that as "March 1, 12:00 AM". Carry a `date_precision` column and make every renderer consult it; false precision on a legal chronology is a defect, not a formatting quirk. (ADR-0005)
- **A Postgres enum created implicitly by `create_table` is never dropped on downgrade** — SQLAlchemy emits `CREATE TYPE` as a side effect of the first table referencing the type, but `drop_table` does not remove it, so downgrade-then-upgrade dies with "type already exists". Declare the enums at module level with `create_type=False`, create them explicitly at the top of `upgrade()` and drop them at the bottom of `downgrade()`, and prove it by round-tripping upgrade → downgrade → upgrade against a real database — a single upgrade run passes either way and tells you nothing. (ADR-0004 migration)
- **Integration tests build their schema from the MIGRATION, never from `metadata.create_all`** — creating tables from the models tests the models against themselves and lets the migration drift away from them undetected, while the migration is what production actually runs. Drive `alembic upgrade head` in the fixture (as a subprocess: `env.py` uses `asyncio.run()`, which cannot be called from inside a running event loop), and verify the fixture against a freshly created database, not just one already at head. (ADR-0004 integration fixture)
- **A model that is never imported is invisible to autogenerate** — `alembic revision --autogenerate` compares the database against `Base.metadata`, and a model module nothing imports has not registered itself, so it is silently missing from the migration that should have created it. Import the models package in `env.py` for its side effect. (ADR-0004)
- **`unique=True` and `unique=True, index=True` produce different objects with different names** — the first yields a UniqueConstraint (`uq_…`), the second a unique *index* (`ix_…`) and no constraint at all. A test asserting the wrong one passes for the wrong reason or fails confusingly; give each convention its own column. (Phase 0.2 base-conventions test)
